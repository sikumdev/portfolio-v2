한국감정평가사협회 IT정보센터 · 실무 · 2024

매달 10건씩 오던 문의를 줄인 것은 문장 하나였습니다

회원사 업무 시스템의 '전자서명 오류' 문의가 매달 약 10건씩 반복됐습니다.
시스템이 아니라 사용자의 작업 환경이 원인임을 확인하고,
오류 안내 문구 한 줄을 바꿔 문의를 월 1~2건으로 줄였습니다.

내 역할
사용자 지원원인 분석개선 요청

문제

문의는 반복됐고, 해결은 매번 사람이 붙어야 했습니다

회원사(전국 감정평가법인·사무소)가 쓰는 업무 시스템의 사용자 지원을 맡고 있었습니다. "전자서명이 안 됩니다"라는 문의가 매달 약 10건씩 왔고, 그때마다 담당자가 개별로 붙어 해결해 주는 식으로 처리되고 있었습니다.

재현 불가

내 환경에서 여러 조건으로 시도해도 오류가 나지 않음.

공통점 없음

문의자의 PC 사양·OS 버전이 제각각

사람 의존

매 건 담당자가 대응 — 시간이 그대로 소모

판단

실마리는 한 사용자의 '밖에서 작업 중'이라는 말이었습니다

문의 관리 프로그램에서 해당 건만 추려 환경을 비교했지만 공통점이 없었습니다. 그러다 한 사용자가 지나가듯 "밖에서 작업 중"이라고 했고, 사무실 밖이라면 접속 환경이 다를 테니 그게 원인일 수 있겠다고 생각했습니다. 다른 환경에서 직접 서명을 시도해 보니 같은 오류가 재현됐고, 전자서명이 허용된 접속 환경에서만 동작하도록 되어 있다는 것을 그때 알게 됐습니다. 그 뒤로 문의마다 작업 장소를 먼저 물었고, 원인이 시스템이 아니라 허용되지 않은 환경에서 시도한 것임을 확정했습니다.

처음 가설

프로그램 버그 또는 특정 OS·브라우저 호환 문제 → 환경 비교로 검증 → 기각

확정 원인

사용자가 조건에 맞지 않는 환경에서 시도 → 오류 문구만 뜨고, 왜 안 되는지는 알려주지 않음

전자서명 문의는 작업 환경을 먼저 확인하는 순서로 매뉴얼을 고쳤습니다.

결과

지성 + 백탁 없음, 건성 + 보습, 민감성 + 순함. 조건을 바꿔도 1위는 항상 같은 제품이었습니다. 그런데 평가 점수는 100%였습니다.

원인

점수에 "언급 수 ÷ 리뷰 수"를 곱하고 있었습니다. 그 제품은 리뷰 한 건에 기준을 평균 4.75개 언급했고(다른 제품 중앙값 2.53개), 리뷰가 길다는 이유만으로 모든 점수가 2배 가까이 부풀었습니다.

해결

언급 수는 점수에 곱하지 않고 "믿을 만한가"를 판단하는 데만 썼습니다. 기준별로 점수 범위를 맞추고, 사용자가 말한 조건의 비중을 60%에서 85%로 올렸습니다. 같은 함수에서 버그 3개도 함께 고쳤습니다.

질문하면 SQL을 만들고, 못 하면 이유를 말하는 리포트 에이전트

"고객 유형별 고객 수 알려줘"처럼 자연어로 물으면 에이전트가 DB 스키마를 바탕으로 SQL을 생성하고, 실행 가능하다고 판정된 경우에만 PostgreSQL에서 조회해 리포트로 요약합니다. 실행하면 안 되는 요청은 거부하고 사유를 돌려줍니다.

문제

데이터는 DB에 있는데, 질문할 때마다 SQL을 아는 사람을 찾아야 합니다

비개발 동료가 "지난달 VIP 고객 매출 얼마야?"를 알고 싶을 때, SQL을 모르면 요청을 넣고 기다려야 합니다. LLM에게 SQL을 쓰게 하면 빨라지지만, 생성된 SQL을 그대로 DB에 실행하는 건 다른 문제입니다.

위험

LLM이 UPDATE · DELETE를 만들어 실행하면 되돌릴 수 없습니다.

모호함

"잘 나가는 상품"처럼 정의가 없는 질문에도 그럴듯한 SQL을 만듭니다.

분기 불가

LLM의 자유 텍스트 응답으로는 "실행할지 말지"를 노드가 판단할 수 없습니다.

판단

에이전트는 SQL을 '제안'만 하고, 실행 여부는 구조화된 판정값으로 결정합니다

시스템 프롬프트테이블 구조 · 컬럼 설명 · 금지 행위(UPDATE / DELETE) · 허용 범위(조회)를 명시. 범위 밖 요청은 SQL을 만들지 말고 거부하도록 지시 — 이 프롬프트가 에이전트의 헌법
Output Parser응답을 { SQL, success, reason } JSON으로 강제. success=false면 SQL은 비어 있어도 되고 reason은 필수
Switchsuccess가 true일 때만 Execute SQL로, false면 사유를 사용자에게 전달. 거부는 에러가 아니라 의사결정으로 취급
Chat Memory세션별 대화 이력을 Postgres에 저장해 "그중 VIP만"처럼 이어지는 질문을 처리

설계

스키마 자체에 "성공이면 ok, 실패면 사유 필수" 규칙을 넣었습니다

User Chat → SQL 생성 Agent (DB 스키마 이해 + 거부 가능) → Structured Output { SQL, success, reason } → Switch ├─ success = true → Execute SQL → Aggregate → 결과 분석 · 리포트 생성 └─ success = false → reason 사용자에게 전달 (SQL 실행 ❌)

Output Parser 스키마의 핵심

additionalProperties: false로 정의되지 않은 필드를 차단하고, if success=true → reason = "ok", if success=false → reason minLength 1 조건을 스키마에 넣어 성공 케이스의 일관성과 실패 케이스의 디버깅 가능성을 동시에 확보했습니다.

success = false가 나오는 경우

의도가 불명확한 질문(정의되지 않은 지표), 스키마에 없는 테이블 · 컬럼, 데이터 변경을 요구하는 요청. 이때 SQL은 생성되지 않고 사용자는 "왜 안 되는지"를 받습니다.

리포트 단계 분리

SQL 실행 결과는 Aggregate로 묶은 뒤 별도 LLM 노드가 "결과 분석 및 리포트 생성"을 맡습니다. SQL을 만드는 에이전트와 결과를 해석하는 모델의 역할을 나눴습니다.

JSON.stringify

조회 결과(객체 배열)를 리포트 프롬프트에 넣기 위해 문자열로 직렬화했습니다. 빠뜨리면 모델이 [object Object]를 받습니다.
